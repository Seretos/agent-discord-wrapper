# agent-discord-wrapper

Pure skill plugin — no binary of its own. It wraps the **external Discord MCP server** ([HardHeadHackerHead/discord-mcp](https://github.com/HardHeadHackerHead/discord-mcp), MIT, npm `@quadslab.io/discord-mcp`): the MCP is declared inline in the `mcpServers` block of **both** `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json`, and `skills/discord-wrapper/SKILL.md` teaches the agent the parts of the server that are not self-explanatory from its tool schemas. The host agent launches the server automatically via `npx`.

## Contracts an agent won't infer from the tree

- **Two secrets travel two different paths, and that asymmetry is deliberate.** Claude Code declares `bot_token` (`sensitive: true`, `required: true`) and `guild_id` (`required: true`, not sensitive) as `userConfig` options and substitutes `${user_config.bot_token}` / `${user_config.guild_id}` into the server's `env`. Codex has no `userConfig` equivalent, so its manifest ships **no `env` block at all** and the server inherits `DISCORD_TOKEN` / `DISCORD_GUILD_ID` from the launching process. Adding an `env` block to the Codex manifest to "fix the asymmetry" would either hardcode a secret into the repo or set the variable to an unexpanded literal. `${user_config.*}` is only expanded in MCP/LSP configs and hook `args`; it is rejected in shell-form commands, so the values must stay in `env`, never in `command`/`args`. This is the same pattern as `agent-meshy-wrapper` — see that plugin's `AGENTS.md` for the fuller rationale.
- **The bot token is never stored in the repository or in `settings.json`.** `sensitive: true` routes it to the OS keychain (or `~/.claude/.credentials.json`); `guild_id` is not sensitive and lands in `settings.json` under `pluginConfigs`. Claude Code reads `pluginConfigs` only from user settings, `--settings`, and managed settings — a project's `.claude/settings.json` is ignored for this, so neither value can be supplied per-repo.
- **The server binds to exactly one Discord guild.** `DISCORD_GUILD_ID` is required at connect time; there is no per-tool guild parameter. Operating on a second Discord server means a second install of this plugin with a different `guild_id` (Claude Code supports installing the same plugin under different names/configs, or running a second bot application) — it is not a configuration the server itself supports.
- **Both privileged gateway intents are requested unconditionally.** The server asks for the Server Members intent and the Message Content intent on every connect, regardless of which tools are actually used. If either is left off in the Discord Developer Portal (Application → Bot → Privileged Gateway Intents), Discord closes the gateway connection with close code `4014` and *every* tool call fails, not just the ones that need the intent. This is not configurable from the plugin side.
- **`send_message_with_file`'s `fileUrl` parameter accepts a local filesystem path despite its name and its own schema description.** Under the hood the server builds a discord.js `AttachmentBuilder`, whose resolver branches on `/^https?:\/\//` — anything else is resolved as a local path and read off disk. The tool's own JSON schema says "URL of the file to attach", which is incomplete and will mislead a model that only reads the schema. `SKILL.md` documents the real behavior; do not let it drift back to schema-literal wording. `send_embed`'s `image` field, by contrast, genuinely only accepts a URL — the two tools are not interchangeable for local files.
- **Channel arguments accept fuzzy name matching, not just IDs.** A misspelled or ambiguous channel name can silently resolve to the wrong channel. Prefer passing channel IDs from calling code/skills over names.
- **The version pin is exact on purpose.** `@quadslab.io/discord-mcp@2.1.1` in both manifests lets `npx` reuse one cached package instead of re-resolving against the registry on every cold start — the same reasoning as `agent-meshy-wrapper`, `agent-blender-wrapper`, `agent-unity-wrapper`. Bumping it means editing both manifests and re-checking `SKILL.md`'s tool-category table against the new release notes; `lint.yml` only checks that the two manifests match each other, not that the pin is current.
- **This is a small, single-maintainer package (27 stars at the time of writing).** There is no vendor fallback in this ecosystem if it goes unmaintained — the runner-up considered during selection (`discord-mcp-agent` on PyPI) is locked to a single fixed channel via env var and has no channel/role/thread management, so it is not a drop-in replacement for the full-access scope this plugin ships.
- **Release is orphan-branch + marketplace dispatch.** `release.yml` (manual: Actions → release → `version=X.Y.Z`) stamps the version into both manifests, force-pushes an orphan `release` branch holding only install-ready files, and POSTs a dispatch (`category: skill`, `tags: ["discord","communication","chat"]`) to `Seretos/agent-marketplace`. `main` and `release` share no history. Clients install at the tag `agent-discord-wrapper--vX.Y.Z`.
- **Required secret:** `MARKETPLACE_DISPATCH_TOKEN` — fine-grained PAT, `Contents: RW` + `Pull requests: RW` on `Seretos/agent-marketplace` only.
- **`assets/icon.png` and `description.md` are release artifacts, not just repo files.** The dispatch payload sends `raw.githubusercontent.com/${repo}/${TAG}/assets/icon.png` and `.../description.md`, so both must live on the orphan `release` branch at the tagged commit — `release.yml`'s stage step copies them in for exactly that reason.
- **Depending on an MCP plugin:** declare it under `dependencies` in `.claude-plugin/plugin.json` (`{ "name": "agent-<mcp>", "version": ">=0.0.1 <1.0.0" }`). The Discord server is wired directly via `mcpServers` in both manifests (not via `dependencies`), which is why `dependencies` stays `[]`.
